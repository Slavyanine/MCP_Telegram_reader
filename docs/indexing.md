# Индексированный поиск и голосовые

## Включение и отключение

В административный `config.json` добавьте секцию (остальные поля и ACL остаются прежними):

```json
"indexing": {
  "enabled": true,
  "database": "/var/lib/telegram-acl-mcp/index.sqlite3",
  "history_since": "2026-06-23T00:00:00+03:00",
  "sync_interval_seconds": 30,
  "page_size": 100,
  "transcribe": true,
  "backend": "telegram",
  "request_interval_seconds": 2,
  "max_attempts": 8,
  "max_pending_polls": 60,
  "max_queue_size": 10000,
  "max_results": 50,
  "max_context": 10
}
```

Замените дату начала на нужную. Если `history_since` отсутствует, при первом запуске база фиксирует начало как «сейчас минус `history_days`» (по умолчанию 90). При последующих запусках это начало сохраняется: автоматического удаления сообщений старше 90 дней нет. Изменение `history_days` влияет только на новую базу. Для изменения периода существующей базы явно задайте `history_since`: прогресс загрузки будет сброшен, более ранние сохранённые сообщения удалены при сужении периода.

Для отключения достаточно:

```json
"indexing": { "enabled": false }
```

Либо удалите всю секцию. После перезапуска сервер:

- объявляет только исходные пять инструментов;
- отклоняет прямые вызовы индексированных инструментов, даже если клиент сохранил их описание;
- не открывает и не создаёт SQLite, не запускает синхронизацию и транскрибацию;
- возвращает прежний формат сообщений без полей транскрипции и метаданных индекса.

Уже существующая БД при отключении сохраняется на диске, но не используется. После повторного включения обработка продолжается. Каталог `StateDirectory` может существовать и при отключённом режиме; это не означает, что создана БД.

Все настройки читаются при запуске; переключение режима требует перезапуска службы и обновления списка MCP-инструментов/переподключения Hermes. Отдельного переключателя в Hermes нет.

`transcribe=false` при `enabled=true` оставляет индекс текста, имён файлов и ссылок, но выключает очередь транскрибации, скрывает инструмент расшифровки и исключает ранее сохранённые транскрипции из выдачи и поиска. Они сохраняются в БД для последующего включения.

## Yandex SpeechKit без Telegram Premium

Для коротких голосовых можно вручную выбрать `backend: "yandex"`. Файл `deploy/indexing.yandex.example.json` содержит значение секции `indexing` для вставки в основной конфиг, а не самостоятельный конфиг сервера. Пример секции:

```json
"indexing": {
  "enabled": true,
  "database": "/var/lib/telegram-acl-mcp/index.sqlite3",
  "transcribe": true,
  "backend": "yandex",
  "yandex": {
    "api_key_file": "/etc/telegram-acl-mcp/yandex-api-key.secret",
    "language": "ru-RU",
    "timeout_seconds": 30
  }
}
```

1. Подготовьте каталог Yandex Cloud с подключённым биллингом и сервисный аккаунт с ролью `ai.speechkit-stt.user` на каталог. Создайте для него API-ключ с доступом к распознаванию речи согласно [инструкции Yandex](https://yandex.cloud/ru/docs/speechkit/concepts/auth).
2. Сохраните ключ в отдельном файле, доступном службе `telegram-mcp`: на Linux владелец `root`, группа `telegram-mcp`, права `0640`. Родительские каталоги должны принадлежать root и не разрешать запись другим пользователям, как и для остальных секретов проекта. Значение ключа в JSON не помещается.
3. Измените секцию `indexing`, задайте нужный `history_since` и перезапустите службу. Переподключите MCP-клиент для обновления описания инструментов.
4. Проверьте `telegram_get_index_status`, затем результат на коротком собственном голосовом сообщении.

Ключ читается только при одновременно включённых `enabled`, `transcribe` и `backend: "yandex"`. Для сервисного аккаунта `folderId` не передаётся. Настройки языка и таймаута проверяются при активном Yandex backend; допустимый таймаут — 1–300 секунд, по умолчанию 30. Поддержку выбранного языка определяет SpeechKit.

Поддерживаются только одноканальные голосовые OggOpus длительностью до 30 секунд включительно. Локальный предел размера — 1 000 000 байт (консервативная трактовка лимита API 1 МБ). Проверяются метаданные до скачивания, фактический объём, Ogg/Opus-заголовок и длительность по Ogg granule position. Аудио скачивается в ограниченный буфер памяти и передаётся по HTTPS в [синхронный REST API v1](https://yandex.cloud/ru/docs/speechkit/stt/api/request-api). Аудиофайлы на диск не записываются; ffmpeg, SDK Yandex и Object Storage не требуются. Видеокружки, другие форматы и длинные записи не конвертируются, не обрезаются и не разбиваются.

Синхронность относится к одному запросу SpeechKit: текст приходит в его ответе. MCP-инструмент по-прежнему сразу возвращает кэш или ставит задание в очередь. Последовательный worker ожидает HTTP асинхронно, вне блокировки Telegram RPC. Распознавание **автоматически обрабатывает также историю в заданном периоде**, если у записей ещё нет готовых транскрипций; обращения к SpeechKit тарифицируются провайдером.

Ошибки `audio_too_long`, `audio_too_large`, `unsupported_media`, `invalid_media_metadata`, `empty_transcript` и `yandex_request_rejected` завершают задание со статусом `failed`. Сетевые ошибки, HTTP 429/5xx и некорректные ответы повторяются с увеличением задержки, не более `max_attempts`. Ошибки HTTP 401/403 устанавливают `transcription_blocked_reason: "yandex_auth_failed"` и останавливают обращения к SpeechKit, сохраняя очередь. После исправления ключа или прав перезапустите службу. Чтение и синхронизация текста продолжаются. `pending` и `max_pending_polls` используются только Telegram backend.

Для возвращения на Telegram установите `backend: "telegram"` и перезапустите службу. Автоматического перехода между провайдерами нет. Готовые транскрипции остаются с исходным `transcript_source` (`telegram`, `yandex` или `deepgram`) и не распознаются повторно. При смене backend незавершённые задания получают сброшенные счётчики и задержки; задания `failed` требуют явного `retry_failed: true`. Смена backend не меняет ACL и период истории.

## Deepgram без Telegram Premium

Администратор выбирает один из трёх backend: `telegram` (по умолчанию), `yandex` или `deepgram`. Для Deepgram добавьте секцию из [примера](../deploy/indexing.deepgram.example.json) в поле `indexing` основного конфигурационного файла. Это значение секции, а не самостоятельный конфиг сервера:

```json
"indexing": {
  "enabled": true,
  "database": "/var/lib/telegram-acl-mcp/index.sqlite3",
  "transcribe": true,
  "backend": "deepgram",
  "deepgram": {
    "api_key_file": "/etc/telegram-acl-mcp/deepgram-api-key.secret",
    "model": "nova-3",
    "language": "ru",
    "smart_format": true,
    "timeout_seconds": 120,
    "download_timeout_seconds": 120,
    "max_audio_bytes": 25000000,
    "max_audio_duration_seconds": 3600
  }
}
```

1. Создайте API-ключ проекта Deepgram с доступом к распознаванию и обеспечьте достаточный баланс. См. [начало работы с API](https://developers.deepgram.com/docs/pre-recorded-audio).
2. Сохраните ключ отдельным файлом: на Linux владелец `root`, группа `telegram-mcp`, права `0640`; родительские каталоги принадлежат root и не разрешают запись другим пользователям. В JSON указывается только абсолютный путь к ключу.
3. Задайте нужный период истории, выберите `backend: "deepgram"`, перезапустите службу и переподключите MCP-клиент.
4. Проверьте `telegram_get_index_status`: `backend` должен быть `deepgram`, `transcription_blocked_reason` — `null`. Поставьте собственное русское голосовое через `telegram_transcribe_voice`, затем проверьте готовый текст, `transcript_source: "deepgram"` и поиск контрольной фразы. Telegram Premium не требуется.

Ключ читается только при одновременно включённых `enabled`, `transcribe` и выбранном `deepgram`. Секции `yandex` и `deepgram` могут присутствовать одновременно; секрет неактивного провайдера не читается. Параметры активного Deepgram проверяются при запуске: неизвестные поля и ключ в JSON запрещены, `smart_format` должен быть boolean. Модель задаётся непустым идентификатором до 64 символов (строчные латинские буквы, цифры, дефис, подчёркивание), язык — кодом вроде `ru`, `en-US` или `multi`. Доступность конкретного сочетания определяет API; по умолчанию используется `nova-3` / `ru`.

Поддерживаются только одноканальные голосовые OggOpus. Байты отправляются без перекодирования в [Deepgram Listen API](https://developers.deepgram.com/reference/speech-to-text/listen-pre-recorded): `POST /v1/listen`, `Content-Type: audio/ogg`, `Authorization: Token …`. SDK, ffmpeg, временные аудиофайлы и публичные URL не используются. Видеокружки и аудиовложения других типов не поддерживаются.

Пределы 25 000 000 байт и 3600 секунд — локальные ограничения приложения, а не лимиты провайдера. Проверяются метаданные, фактический объём, структура Ogg/Opus и длительность по granule position. Администратор может задать `max_audio_bytes` в пределах 1–100 000 000 и `max_audio_duration_seconds` в пределах 1–14400. Память на аудио ограничена буфером; HTTP-клиент и проверки также используют память, поэтому лимит файла не равен пределу памяти процесса. Превышение лимита завершает задание без обрезки или разбиения записи.

`timeout_seconds` ограничивает HTTP-запрос Deepgram, `download_timeout_seconds` — скачивание из Telegram; оба принимают целые значения 1–600 секунд, по умолчанию 120. Скачивание и HTTP-ожидание не удерживают общий Telegram RPC-lock; FloodWait откладывает новые обращения к Telegram. Worker обрабатывает задания последовательно. MCP сразу возвращает кэш или состояние очереди, не ожидая распознавания; `pending` и `max_pending_polls` относятся только к Telegram backend.

Ошибки и восстановление:

| Причина | Поведение |
|---|---|
| HTTP 401/403 | `deepgram_auth_failed`: остановка обращений к провайдеру, очередь сохраняется |
| HTTP 402 | `deepgram_payment_required`: та же блокировка до пополнения баланса |
| HTTP 429 | `deepgram_rate_limited`: повтор с увеличением задержки; корректный `Retry-After` учитывается как минимум задержки, значение ограничено сутками |
| Сеть, HTTP-таймаут, HTTP 408/422/5xx | `deepgram_unavailable`: ограниченные повторы |
| Некорректный JSON/структура ответа | `deepgram_invalid_response`: ограниченные повторы |
| Остальные HTTP-ошибки | `deepgram_request_rejected`: `failed` |
| Пустой текст, неподдерживаемое или слишком большое/длинное аудио | `empty_transcript`, `unsupported_media`, `audio_too_large`, `audio_too_long`: `failed` |

Повторы ограничены `max_attempts`; после исчерпания задание становится `failed`. Ошибка скачивания из Telegram обрабатывается как `telegram_unavailable`, FloodWait — как `rate_limited`. После исправления ключа, прав или баланса перезапустите службу. Текстовая синхронизация продолжает работать при блокировке Deepgram. В статус и логи не передаются ключ или сырой ответ провайдера. См. [описание ошибок Deepgram](https://developers.deepgram.com/docs/errors).

Обработка автоматически охватывает также историю в настроенном периоде. Запросы оплачиваются у провайдера; после сетевого таймаута или остановки процесса повтор может повторно отправить уже обработанное аудио. При смене backend готовые транскрипции сохраняются. В частности, голосовые, ранее получившие `failed` у Yandex из-за лимита 30 секунд, требуют явного `retry_failed: true` после переключения на Deepgram. Смена модели или языка сама по себе не перераспознаёт готовый кэш. Для отката выберите `telegram` либо `yandex` и перезапустите службу; миграция SQLite не требуется.

## Инструменты

| Инструмент | Условие доступности | Назначение |
|---|---|---|
| Пять исходных методов | Всегда | Прямое чтение и текстовый поиск Telegram |
| `telegram_search_context` | `indexing.enabled=true` | Поиск по локальному индексу всех разрешённых или выбранных чатов |
| `telegram_get_index_status` | `indexing.enabled=true` | Период истории, прогресс и ошибки синхронизации, готовность голосовых |
| `telegram_transcribe_voice` | Также `transcribe=true` | Возврат готовой транскрипции или постановка приоритетного задания |

Пример аргументов `telegram_search_context`:

```json
{
  "query": "отчет",
  "outgoing_only": true,
  "date_from": "2026-09-01T00:00:00+03:00",
  "sources": ["text", "voice", "filename", "url"],
  "limit": 20,
  "context_before": 2,
  "context_after": 2
}
```

`chat_keys` по умолчанию содержит все чаты ACL; можно передать непустой список выбранных ключей. Никакого обнаружения других чатов нет. `sender_id` фильтрует автора, `outgoing_only` — сообщения владельца используемой Telegram-сессии. Даты относятся к отправке сообщения, а не к сроку поручения. Интервал `[date_from, date_to)`, даты обязательно с часовым поясом.

Все разделённые пробелами фрагменты запроса должны встретиться в выбранных полях одного сообщения. Поиск использует SQLite FTS5 trigram, Unicode NFKC, регистр не учитывается, `е` и `ё` эквивалентны. Поиск по подстрокам поддерживает `отчет` → `отчета`, фрагменты имени и URL. Это не полноценный морфологический или семантический поиск: `отчета` не обязательно найдёт `отчет`, а `доклад` не станет синонимом автоматически. Hermes должен использовать основы слов и несколько запросов с синонимами. FTS-операторы из пользовательского ввода не исполняются: фрагменты воспринимаются буквально. Очень широкие запросы ограничены по времени; при отказе сузьте период или запрос.

Выдача содержит `chat_key`, сообщение, `matched_sources`, фрагменты совпадений и контекст. `reply_to` содержит исходное сообщение ответа, если оно есть в индексе того же чата. Контекст не обходит другие чаты и не восстанавливает всю ветку обсуждения.

Для следующей страницы передайте `next_cursor` как `cursor`, сохранив остальные аргументы. Курсор привязан к запросу, области доступа и версии индекса. Если индекс изменился, сервер попросит начать поиск заново — это предотвращает незаметные пропуски при изменении сортировки по релевантности.

Пример вызова `telegram_transcribe_voice`:

```json
{ "chat_key": "project_a", "message_id": 123 }
```

Метод не ждёт завершения расшифровки. Если очередь заполнена, сообщение может иметь `not_queued`; фон поставит его в очередь после освобождения места. Состояния: `not_queued`, `queued`, `processing`, `pending`, `ready`, `failed`, а при отключённой транскрибации — `disabled`. После выяснения причины ошибки можно повторить с `"retry_failed": true`; обычный повторный вызов не сбрасывает лимит попыток. Сообщения вне заданного периода истории этим методом не индексируются.

Транскрипция отделена от текста/подписи и помечена как машинная, не дословная цитата. Исходное сообщение не изменяется. `telegram_transcribe_voice` помечен в MCP как инструмент с побочным действием: он может изменить локальную очередь и инициировать распознавание у выбранного провайдера; остальные методы чтения остаются read-only.

## Полнота и актуальность

В `coverage` и статусе по каждому чату доступны:

- `history_since`, `history_done`, фактически самая ранняя и поздняя даты;
- `last_sync` — время последнего опроса, догнавшего новые сообщения;
- `last_reconciled` — время завершения полного прохода сверки загруженного периода;
- количество голосовых, готовых транскрипций, недоступных транскрипций и состояния очереди;
- безопасный код ошибки синхронизации без содержания сообщений и секретов.

`incomplete_reasons` объясняет известные пробелы. Поиск без нижней даты явно предупреждает об истории до `history_since`. Даже если список причин пуст, индекс является периодически обновляемым состоянием, а не транзакционным снимком Telegram. Hermes должен учитывать время последнего обновления и не трактовать пустую выдачу как доказательство отсутствия поручения.

Сначала загружаются последние сообщения, затем старая история страницами. Новые сообщения обрабатываются по отдельному курсору, чтобы заполнение истории их не блокировало. Недавние сообщения перепроверяются в каждом цикле; после первичной загрузки старые диапазоны сверяются по кругу. Поэтому изменения и удаления старых сообщений отражаются с задержкой полного прохода. Удаление из индекса выполняется только для успешно прочитанного диапазона, не при сетевой ошибке. Получение соседнего контекста из индекса может быть неполным.

На вопрос «кому я поручил отчёт на завтра» следует искать собственные сообщения по основам слов, читать контекст и указывать `chat_key` + `message_id`. Значение «завтра» в исходном поручении определяется относительно даты сообщения и часового пояса, а не автоматически относительно сегодняшнего дня. Если работал отдельный аккаунт, `outgoing_only` относится к нему; для поиска поручений вашего личного аккаунта нужен его `sender_id` и доступ служебного аккаунта к соответствующим сообщениям.

## Транскрибация

По умолчанию используется native backend `telegram`: `messages.TranscribeAudioRequest`. Для этого backend Premium нужен у аккаунта серверной Telegram-сессии; Yandex работает без Premium. При отсутствии Premium текстовая индексация продолжает работать, задания сохраняются, статус показывает `premium_required`; наличие Premium повторно проверяется примерно раз в пять минут.

При `backend: "telegram"` аудио не скачивается нашим сервером и не отправляется сторонним STT-провайдерам. Распознаются также видеосообщения-кружки. При `backend: "yandex"` короткие голосовые скачиваются и отправляются в SpeechKit по правилам выше. При `backend: "deepgram"` голосовые скачиваются в память и передаются Deepgram с настроенными ограничениями размера и длительности. Содержимое документов не читается, URL извлекаются из текста, entities, метаданных уже полученного preview и URL-кнопок без открытия страниц или нажатия кнопок.

Фоновая задача делает один запрос транскрибации за попытку. В Telegram backend `pending` сохраняется в SQLite и опрашивается повторно; частичный текст не попадает в индекс как готовый. `FloodWait` откладывает фоновые запросы, временные ошибки повторяются с увеличением задержки. Неудачные и слишком долго ожидающие задания получают `failed`. Очередь и результаты переживают перезапуск, незавершённые задания возвращаются в очередь. Замена голосового вложения инвалидирует старую транскрипцию.

Служба использует один процесс, один Telethon-клиент, две фоновые asyncio-задачи и постоянную очередь SQLite. Ожидания фоновой работы не удерживают блокировку исходного `Reader`. Блокировка файла БД запрещает случайный параллельный запуск второго экземпляра на той же базе. SQLite-операции выполняются короткими транзакциями без сетевых ожиданий. Другая Telegram-учётная запись требует другой базы; несовпадение account ID останавливает запуск индексированного режима.

## Развёртывание и хранение

Для HTTP-запросов SpeechKit используется прямая зависимость `httpx==0.28.1`, уже присутствующая в `requirements.lock`. Нужна сборка SQLite с FTS5 и tokenizer `trigram` (SQLite 3.34+). Отсутствие поддержки обнаруживается при создании базы; сервер не подменяет индексированный режим скрытым текстовым fallback. В комплектном systemd unit добавлены:

```ini
StateDirectory=telegram-acl-mcp
StateDirectoryMode=0700
```

Это разрешает службе запись в `/var/lib/telegram-acl-mcp` при `ProtectSystem=strict`. Путь по умолчанию не требует ослаблять защиту `/opt` или `/etc`. Если нужен другой путь, администратор должен отдельно обеспечить права и разрешить запись через systemd. На Windows задайте абсолютный путь и ограничьте ACL каталога средствами Windows.

После установки обновлённого пакета и unit администратор выполняет:

```bash
systemctl daemon-reload
systemctl restart telegram-acl-mcp
systemctl status telegram-acl-mcp --no-pager
```

Затем переподключите Hermes к MCP, вызовите `telegram_get_index_status` и дождитесь нужного покрытия. Сначала проверьте качество транскрипций выбранного backend на собственных записях: особенно имена, даты и окончания фраз. Автоматические тесты используют имитацию Telegram и SpeechKit; они не подтверждают качество распознавания конкретных аудиозаписей.

База содержит незашифрованный текст переписки. Не монтируйте каталог БД в контейнер Hermes; храните его у служебного пользователя. При старте включённого режима данные чатов, отсутствующих в текущем ACL, удаляются из активных таблиц и поиска. Это логическое удаление, а не гарантированное стирание блоков диска или резервных копий. При отключённом режиме очистки БД нет, поскольку она вообще не открывается.

Для резервного копирования остановите службу, скопируйте каталог состояния целиком вместе с SQLite WAL/SHM, затем запустите службу. Для восстановления остановите службу, восстановите согласованную копию и права служебного пользователя, затем запустите её. Не копируйте только основной файл активной WAL-базы. Очередь и прогресс синхронизации входят в резервную копию. Файл `.lock` не хранит постоянную блокировку: ОС освобождает её при завершении процесса.

Для полного перестроения администратор может указать новый путь БД и перезапустить службу. Старую БД удаляют отдельно по принятой политике хранения. Конфигурация и секреты продолжают принадлежать администратору; Hermes не получает инструментов изменения ACL, настроек, файлов БД или запуска произвольного SQL.
